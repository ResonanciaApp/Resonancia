1. Autenticación y cuentas de usuario
Lo que YA hay:

✅ Registro y login funcionando vía Clerk (email/contraseña, Google, Apple).
✅ Recuperación de contraseña (la maneja Clerk automáticamente).
✅ Sistema "híbrido": el usuario puede usar casi toda la app de forma local/anónima (onboarding con nombre, año de nacimiento, email) sin crear cuenta en la nube. La cuenta Clerk solo se necesita para lo social (amigos, mezclas comunitarias, chat).
✅ Tabla users en la base de datos (id, clerk_user_id, username, display_name, email, avatar_url, fechas).
Lo que FALTA:

⚠️ No hay distinción real entre perfil "público" y "privado" — hoy si entrás a lo social, tu perfil es visible.
Implicancia: Esta parte está prácticamente resuelta. No requiere trabajo grande. Es la base más sólida que tenés.

✅ Perfil en servidor con username, display_name, avatar (foto sube a Object Storage).
✅ Sincronización local↔servidor (ProfileSync).

❌ "Contenidos escuchados" y "estadísticas" mostrados en el perfil público — hoy las stats son solo locales (ver punto 4).
❌ Contador de seguidores/seguidos en el perfil (ver punto 3).
Implicancia: El perfil base está, pero para mostrar stats/seguidores públicamente hay que mover esos datos al servidor primero.

3. Sistema de seguidores
Lo que YA hay:

✅ Existe un sistema de amistad bidireccional (solicitar → aceptar), con tabla friendships. Es simétrico: los dos tienen que aceptar.
Lo que FALTA:

❌ El prompt pide seguidores asimétricos (yo te sigo sin que vos me sigas, tipo Instagram/Insight Timer). Eso es un modelo distinto al de amistad que ya tenés.
❌ Contadores de seguidores/seguidos.
❌ Feed personalizado basado en a quién seguís.
Implicancia: Tenés dos caminos: (a) reusar el sistema de amigos que ya funciona, o (b) agregar un modelo de "follow" separado además de los amigos. La opción (b) es más trabajo y puede confundir al usuario (¿amigos Y seguidores?). Decisión de producto importante antes de tocar código.

4. Estadísticas del usuario
Lo que YA hay (TODO local en el dispositivo):

✅ Racha de días consecutivos (actual y máxima).
✅ Tiempo total escuchado.
✅ Cantidad de sesiones/reproducciones.
✅ Categoría más escuchada.
✅ Heatmap de actividad (8 semanas).
✅ Historial de reproducciones (últimas 50).
✅ Progreso por sesión (retoma donde quedaste, marca completadas al 97%).
✅ Pantalla "Tu Progreso" ya construida mostrando todo esto.
Lo que FALTA:

❌ Todo esto vive solo en el teléfono. Si el usuario cambia de dispositivo o reinstala, pierde todas sus stats. No se sincroniza con el servidor.
❌ Registro detallado de cada reproducción en la base de datos (el prompt pide guardar: id usuario, id contenido, fecha/hora, duración, si completó, desde qué sección, tipo de contenido).
❌ "Audio/sesión más reproducida" como dato persistente.
Implicancia: Esta es una de las partes más importantes. Hoy funciona muy bien localmente, pero para que las stats sobrevivan a un cambio de teléfono, salgan en el perfil público, o alimenten rankings/recomendaciones, hay que crear tablas en el servidor (playback_history, user_stats) y empezar a enviar cada reproducción al backend. Trabajo medio-grande, pero la lógica de cálculo ya está hecha — solo hay que "subirla a la nube".

Lo que YA hay:

⚠️ Casi nada. Hay "badges de ADMIN" hardcodeados para grupos (cosmético) y chequeos de "esto es mío" para borrar tus propios comentarios/mezclas.
Lo que FALTA:

❌ Sistema real de roles (usuario normal / creador / administrador).
❌ Tabla de roles y permisos.
❌ Lógica que controle qué puede hacer cada tipo de usuario.
Implicancia: Esto es prácticamente desde cero. Es el cimiento de todo lo que pide el prompt sobre "creadores que suben contenido" y "admin que aprueba". Sin esto, nada de los puntos 6, 7 y 12 funciona.

6. Subida de contenido por usuarios (Panel de Creador)
Lo que YA hay:

✅ Infraestructura técnica de subida de archivos (imágenes y audio) a Object Storage — se usa hoy para fotos de perfil y audios del chat.
✅ Los usuarios SÍ pueden crear cierto contenido: mezclas propias (mixer), actividades de comunidad, entradas de diario.
Lo que FALTA:

❌ No existe un "Panel de Creador" para subir audios/sesiones propias al catálogo.
❌ No existe el flujo: subir → "pendiente de revisión" → admin aprueba → se publica.
❌ Estados de contenido (borrador, pendiente, aprobado, publicado, rechazado).
Implicancia: Esta es la parte más grande y nueva del prompt. Hoy todo el catálogo (sesiones, meditaciones, sonidos) está escrito a mano por vos en el código — no se carga desde una base de datos. Para que usuarios suban contenido, hay que:

Mover el catálogo entero del código a la base de datos.
Construir el panel de subida.
Construir el flujo de revisión/aprobación.
Es un proyecto en sí mismo. Y abre temas legales/operativos importantes (ver "Implicancias generales" al final).
